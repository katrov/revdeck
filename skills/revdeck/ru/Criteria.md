# Критерии и процедуры проверки

Критерий оценки кода — канонические документы репозитория, а не общие best practices. Этот файл не
пересказывает правила и не вводит новых: он определяет, какие документы обязательны для каких путей
и как механически проверить код на их соответствие. Формулировку правила и ссылку на раздел брать из
самого документа. Где документ молчит, замечание получает уровень «придирка» или «вопрос»
(раздел 12), а не выдуманное правило.

Документы для конкретных путей вычисляет revdeck: `rules.map` из `.revdeck.yml` и
автообнаружение (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `docs/*`). Готовый список с секциями
приходит в контексте (`rules.markdown`). Не подбирать правила по памяти и не читать весь `docs/`
вместо этого списка.

## 1. Карта изменений

Перед выбором критериев для каждого файла из diff зафиксировать:

- проект/пакет/модуль, к которому относится файл;
- класс файла: прикладной код, состояние/сторы, стили, тесты, сгенерированный код, конфиг сборки
  или инструментов, документация, конфиг AI-продуктов (`.agents`, `.claude`, `.codex`, `.cursor`), CI;
- слой по пути (раздел 3) и статус: новый файл, изменённый, legacy-зона; путь, который документ
  слоем не описывает, так и пометить;
- для монорепозитория — workspace и границы приложения;
- есть ли для пути документ в правилах; если нет — это повод для кандидата в правила (раздел 2).

Карту привести человеку одной таблицей или списком до начала проверок: она определяет, какие
документы читать, и показывает, что ревью учло.

## 2. Обязательные документы по путям

Источник — `rules` из контекста. Для каждого изменённого пути revdeck уже выбрал:

- документы из `rules.map` (glob → документы с необязательной секцией `#Заголовок` или `#L10-L20`);
- либо `rules.sources`, если ни одна строка не подошла;
- либо автообнаруженные документы, если конфиг пуст.

Процедура:

1. Прочитать каждый документ целиком, если секция не указана, и только указанную секцию, если
   указана.
2. Документ не найден или путь не сопоставлен — сказать об этом в итоге и оценивать по запасному
   правилу: корневые `AGENTS.md`/`CONTRIBUTING.md`/README. Отсутствие правила — не повод придумывать
   своё; это кандидат в правила (`Rules.md`).
3. Документы уровней (архитектура, гайд стиля, ADR, README пакета) читать в том объёме, который
   нужен для затронутых разделов. Если правило не относится к изменённому коду (legacy вне области
   применения) — замечание не выставлять (Migration rule, раздел 12).
4. Конфиги (`webpack`, `tsconfig`, `.eslintrc`, `jest.config`, `.husky`, CI) часто не имеют
   нормативного документа: проверять по разделу 6 и по тому, что проект реально использует.
5. Для `.agents/**`, `.claude/**`, `.codex/**`, `.cursor/**`, `devtools/**` и `.devcontainer/**`
   обязательны разделы корневого `AGENTS.md` о сопровождении конфигураций и адаптеров; паритет
   адаптеров — раздел 9.

## 3. Слои и направление зависимостей

Выполнять для каждого изменённого или нового файла внутри слоистых зон. Источник запретов у каждого
проекта свой: таблица слоёв в документе архитектуры, список разрешённых зависимостей или явные
запреты.

Процедура:

1. Определить слой файла по пути и документу проекта. Путь, которого в таблице нет, слоем не
   считается: замечания о направлении его зависимостей — только **вопрос**; дефекты вроде цикла
   импортов (п. 6) оцениваются по сценарию независимо от слоя.
2. Если документ задаёт только цепочку (`features → useCase → state/api`), проверить её, а не
   строить матрицу.
3. Выписать все импорты файла, ведущие в другой слой. Сначала собрать абсолютные импорты и сверить
   первый сегмент с фактической структурой каталогов; относительные `../` разрешить до слоя вручную:
   ```bash
   grep -nE "from '[^.@][^']*'" <файл>          # абсолютные импорты
   grep -nE "from '@/" <файл>                    # алиасы
   grep -nE "import\('|^import '|jest\.mock\('" <файл>   # динамические, side-effect, моки
   ```
   Импорт из legacy-зоны — не запрещён, но отметить в карте, если документ этого не разрешает.
4. Для каждого импорта сверить пару «слой файла → слой импорта» с документом. Запрещённая пара в
   новом файле или добавленных строках — **важно** со ссылкой на документ; та же пара в неизменённых
   строках — не поднимать, но упомянуть в оценке решения, если MR расширяет модуль.
   Распространённость нарушения уровень не снижает: правило применяется к новому коду.
5. Доступ к состоянию из UI: документ проекта определяет, можно ли читать стор напрямую, только
   через селекторы или только через хуки. Нарушение в добавленных строках — **важно**.
6. Публичный API модуля: импорт внутрь чужого модуля в обход `index.ts`/barrel — по документу
   проекта; модулем считать каталог с собственным `index.ts`.
7. Цикл импортов, который замыкает новый импорт (A → B → A): проверить
   `grep -rn "from '<путь к A>'" <путь к B>`. Цикл — **блокер**, только если доказано, что он ломает
   инициализацию (сторы, `undefined` при импорте), иначе **вопрос**.

## 4. Размещение и ответственность

Для каждого нового или заметно изменённого модуля ответить, в тот ли слой он попал. Источник —
разделы документа архитектуры и гайда состояния о зонах ответственности.

Искать неверное размещение:

- сетевые вызовы, `await` или бизнес-условие в сторе/селекторе;
- навигация, DOM и модалки в сторе;
- локальное состояние для данных, нужных другим частям приложения;
- компонент презентационного слоя, импортирующий стор или бизнес-логику;
- хук с префиксом `use` без React-хуков;
- ответственность, которую документ закрепляет за другим слоем.

Замечание — со ссылкой на раздел документа. Если документ молчит, это **придирка** или **вопрос**.

## 5. Переиспользование и прецеденты

Документ проекта (обычно «Принципы изменений» в `AGENTS.md`) запрещает новые абстракции и
зависимости, если задачу решают существующие средства. Поиск выполняется до оценки кода по существу:

1. Для каждой новой функции, хука, компонента и утилиты поискать аналог по имени и ключевым вызовам:
   ```bash
   grep -rln "<ключевой вызов или имя>" <src> --include=*.ts --include=*.tsx | grep -v node_modules
   ```
   Для компонентов — сначала UI-пакет проекта. Найденный аналог, который не использован и не
   доработан, — **важно** с путём к аналогу.
2. Код, повторяющий существующую функцию того же слоя (`grep -rn "<характерная строка>"`), —
   **важно** с предложением вынести общую функцию; повтор между разными слоями — **вопрос**, где
   общему коду место. Для стилей — правило о переиспользовании из гайда стиля.
3. Найти соседний модуль того же слоя с похожей задачей и сравнить структуру, именование и обработку
   ошибок. Расхождение с устойчивым прецедентом без причины — **придирка**, если гайд молчит, и
   **важно**, если прецедент закреплён в гайде. Прецедент, который сам нарушает гайд, новый код не
   оправдывает.
4. Новая зависимость: проверить, что в проекте нет зависимости с той же функцией, что версия
   согласована с lock-файлом, что workspace-ссылки не заменены на версии. Зависимость без
   обоснования — **важно** по «Принципам изменений».

## 6. Вызывающий код и влияние

1. Для каждого изменённого экспортируемого символа (функция, тип, prop, action, selector) найти все
   использования:
   ```bash
   grep -rn "\b<Символ>\b" <src> --include=*.ts --include=*.tsx | grep -v node_modules
   ```
   Проверить, что изменение сигнатуры, семантики `null`/`undefined`, порядка аргументов или формата
   данных не ломает ни одно место. Сломанный вызов, который `tsc` не поймает, — **блокер**.
2. Изменения в общих пакетах затрагивают потребителей: найти их по имени пакета (включая
   `package.json`, storybook и другие приложения) и проверить использования там, а не только в
   приложении из описания.
3. Изменённые сторы: найти подписки (`reaction`/`autorun`/`when`), `computed` и места persist.
   Изменение формы персистируемых данных без миграции — **блокер**, если доказано, что сохранённое
   состояние ломает гидратацию; иначе **вопрос**, что будет с уже сохранённым состоянием.
4. Изменённые обработчики событий/сетевого слоя: проверить всех подписчиков на тот же тип события.
5. Feature-флаги: новое поведение за флагом проверять в обоих состояниях; флаг в продуктовом коде
   мимо конфигурации — замечание по документу.
6. Конфиги резолва модулей: новый alias/path должен быть согласован во всех местах, где проект
   резолвит импорты (`tsconfig`, сборщик, тестовый раннер). Рассинхрон — **блокер**, если ломает
   сборку/типы/тесты; иначе **важно** или **вопрос**, если нормативного требования нет.

## 7. ADR и архитектурные решения

1. Собрать заголовки и статусы ADR: `grep -E '^# |^-\s+Статус:' docs/adr/*.md` (или путь, принятый
   в проекте). Если домен MR совпадает с темой ADR в статусе `Accepted` или `Proposed`, прочитать
   ADR целиком и проверить, что diff не противоречит решению и его «Последствиям». Противоречие
   `Accepted` ADR без нового ADR — **блокер**; противоречие `Proposed` — **вопрос**, и **важно**,
   если решение уже реализовано, а MR расходится с реализацией.
2. Нужен ли новый ADR — по документу проекта о ADR (обычно skill `create-adr`). Если решение
   подпадает под критерии, а ADR не добавлен, — **важно** со ссылкой на документ.
3. Новый ADR в diff проверить по шаблону проекта: структура, статус, связи, уникальность номера
   (`ls docs/adr | cut -d- -f1-2 | sort | uniq -d`).

## 8. Тесты

Требование о тестах берётся из документов проекта. Если нормативного требования нет, отсутствие
теста — не нарушение правила. Процедура:

1. Где тесты: `*.spec.ts(x)`, `*.test.ts(x)` рядом с кодом, в `test/` или `__tests__/` модуля;
   раннер и алиасы — конфиг проекта. Если автотестов в проекте нет, замечания об их отсутствии не
   выставлять.
2. Новый useCase, action, selector, утилита или изменённая ветка логики без теста — **вопрос** к
   автору со ссылкой на прецедент: ближайший `*.spec.*` в том же слое. Для багфикса спросить, каким
   тестом воспроизведён дефект.
3. `test.skip`, `.only`, тест без утверждений, заглушка вместо теста — **важно**, если показан
   сценарий ложного результата; без сценария — **вопрос**. Тест, который не упал бы на коде до
   исправления, — **вопрос**.
4. Изменённые конфиги тестов и моки — влияние на существующие тесты (раздел 6).

## 9. Документация и конфиги AI-продуктов

1. Документация в diff проверяется по «Размещению технических знаний» и «Репозиторным ограничениям»
   корневого `AGENTS.md`: язык, ближайший канонический источник, отсутствие дублей
   (`grep -rn "<ключевая фраза>" docs AGENTS.md */AGENTS.md */docs`), роль TSDoc.
2. Новый или изменённый skill в `.agents/skills/`: tracked-адаптер в каждом формате, для которого в
   репозитории уже есть каталог адаптеров (`.claude/skills`, `.codex/skills`, `.cursor/skills`).
   Отсутствие адаптера — **важно** по разделу об источниках инструкций; расхождение `description`
   между адаптером и скиллом — **придирка**. Содержимое скилла — процедура, а не правила.
   Действия скилла над живыми системами (стенды, аккаунты, учётные данные в tracked-файле) —
   **вопрос**; **блокер** — только для production-доступов и токенов.
3. Изменения ограничений безопасности в одном из конфигов `.claude`, `.codex`, `.cursor`:
   проверить эквивалентные изменения в остальных и в документации контейнера, если она описывает
   механизм.
4. Изменения в `AGENTS.md`: постоянное правило — в `AGENTS.md`; объёмное — в `docs/guides/*` со
   ссылкой; процедура — в `.agents/skills`. Нарушение размещения — **важно**.

## 10. Корректность и безопасность

Это перечень мест, где искать дефекты, а не правила: **блокер** или **важно** требует доказанного
сценария «вход — результат»; без него пункт остаётся **придиркой** или **вопросом**. Проверять по
коду, а не по описанию MR:

- async: необработанные промисы, гонки при повторном вызове, устаревший ответ, перезаписывающий
  новый, отсутствие отмены при размонтировании или смене аргументов;
- состояние: подписки без dispose, мутация состояния вне action, лишние/недостающие observer,
  вычисляемые функции в горячих путях;
- React/UI: зависимости эффектов, эффект вместо вычисления при рендере, утечки обработчиков и
  таймеров;
- типы: `any`, `@ts-ignore`, приведения и `!`, скрывающие реальный `undefined`;
- контракты API: как проект представляет ошибку (`Response<T>`, исключение, `Result`) и что код
  делает с неопределённым payload при ошибке;
- i18n: новый ключ без записи в локали ломает проверку; строка-литерал вместо ключа — по прецеденту
  соседних компонентов;
- безопасность: секреты и токены в коде и конфигах; построение HTML из данных; `window.open`/
  `location.assign` с внешними данными; IPC без проверки отправителя и аргументов; внешние URL в
  картинках, которые уходят просматривающим;
- dev-only код: не попадает ли он в production-сборку и наоборот; единого способа документы могут
  не задавать — сравнить с прецедентами, новый механизм — **вопрос**;
- производительность: подписка на весь стор ради 1–2 полей, нестабильные ссылки в props; прочее —
  только с измерением или воспроизводимым сценарием.

## 11. Оценка решения

Кроме списка замечаний ревью даёт оценку решения в целом. Она не превращается в замечания без
`file:line`, а выдаётся отдельным блоком итога и отвечает на вопросы:

1. Решает ли MR заявленную задачу способом, предусмотренным архитектурой, и в тех слоях, где этому
   коду место.
2. Какие альтернативы были доступны в существующем коде и почему выбранный вариант лучше или хуже.
   Если альтернатива явно лучше по правилам — это замечание уровня **важно**; если спорно — **вопрос**.
3. Что усложнится при следующих изменениях: новая точка дублирования, неявная связь между слоями,
   рост legacy-зоны, новая зависимость.
4. Что сделано хорошо и стоит сохранить при доработке.
5. Нужен ли ADR (раздел 7) и достаточно ли обновлена документация.

## 12. Калибровка уровней

- **блокер** — дефект поведения или регрессия с доказанным сценарием, потеря или порча данных,
  уязвимость, сломанный вызывающий код, сломанные lint/типы/сборка/существующие тесты (с выводом
  команды или указанием строки), противоречие `Accepted` ADR, нарушение «Репозиторных ограничений»
  корневого `AGENTS.md`. Без исправления мержить нельзя.
- **важно** — новое нарушение правила из обязательных документов раздела 2 в новом или изменённом
  коде (слой, доступ к состоянию, стиль, именование, размещение знаний, адаптеры), неиспользованный
  аналог или повтор кода того же слоя, тест-заглушка, unrelated-изменения, расхождение описания с
  diff, которое меняет смысл MR. Исправить до мержа или обоснованно отклонить.
- **придирка** — предпочтение там, где документы молчат, формулировки, опечатки, расхождение с
  прецедентом без правила, недоказанная неэффективность. Автор вправе не исправлять.
- **вопрос** — утверждение автора, которое нельзя проверить по коду, неочевидное намерение,
  альтернатива без преимущества по правилам, отсутствие теста, замечание из треда, не подтверждённое
  кодом, импорт из пути, который слоем не описан.

Нарушение в неизменённых строках legacy-кода уровня не получает: это не замечание к MR. Если MR
добавляет код рядом с таким нарушением и повторяет его, это новое нарушение — **важно**, с
пояснением, что исправлять нужно только добавленный код. Распространённость нарушения в кодовой базе
уровень не снижает: гайды по «Области применения» действуют на новый код.
