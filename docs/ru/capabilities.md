# Возможности и решения

[English](../capabilities.md) | Русский

Этот документ — единое актуальное описание возможностей revdeck и причин, по которым продукт устроен
именно так. Здесь же зафиксированы решения о демон-first архитектуре, скоупах проектов и
кросс-проектных фичах.

## Модель продукта

revdeck — локальный код-ревью для GitLab и GitHub, сделанный вокруг агента. Один пользователь запускает
один демон на хосте; агенты, CLI и браузерный UI — клиенты.

```text
agent (MCP/CLI) ──unix socket──▶ revdeck daemon ──glab/gh──▶ GitLab / GitHub
                                      │
                                SQLite + Svelte UI ◀── человек
```

Ключевые гарантии:

- **Публикует человек.** Агент пишет черновики (выжимку, замечания, ответы, комментарии к строкам).
  Человек подтверждает точный план в UI или CLI на хосте, после чего демон публикует. У моста
  devcontainer нет `publish.approve`/`publish.commit` (`CAPABILITY`), поэтому агент не может создать
  approval.
- **Токены остаются на хосте.** Демон вызывает `glab`/`gh`; токены платформ не передаются по RPC и
  вычищаются из окружения дочерних процессов.
- **Правила проекта явные.** Для изменённых путей revdeck выбирает документы репозитория и конкретные
  секции (`AGENTS.md`, архитектура, гайды, ADR).
- **Одна локальная база.** Ревью, проекты, фичи, черновики, approvals и аудит лежат в SQLite в
  state-каталоге пользователя.
- **Работа агента — только ревью.** Проверки агент только планирует; запускает человек в UI или CLI
  на хосте, мост запрещает `checks.run`. Публикация, резолв и approve остаются за человеком.

## Ревью

- MR GitLab и PR GitHub нормализуются в одну модель: ref, описание, автор, статус, ветки, коммиты,
  diff, треды, комментарии и реакции.
- Открытие ревью по номеру, URL, ссылке проекта или текущей ветке; несколько ревью за один вызов.
- Локальная очередь триажа с кешем снимков; фоновый sync и SSE обновляют UI. UI сразу открывает ревью
  из кеша, а устаревший снимок обновляет в фоне — открытие не ждёт `glab`/`gh`. Фоновые обновления
  вливаются в текущее ревью, поэтому загрузчики вкладок (Rules, Analytics, Diff) не перезапускаются на
  каждый SSE/поллинг. Heartbeat'ы SSE отключают поллинг-страховку, а события review/feature/project
  обновляют только свою часть.
- Шапку можно свернуть вручную кнопкой в шапке. Пока она скрыта, кнопка возврата в строке вкладок
  показывает её обратно; таймер авто-скрытия не раскрывает ручное сворачивание.
- Шапка ревью сворачивается при прокрутке вниз и плавно возвращается вверх; вкладки разделов
  остаются видимыми. Тот же паттерн используется там, где есть большой хедер страницы; вкладка Diff
  подключает свой вложенный скроллер (колесо, скроллбар и клавиатура) к тому же обработчику.
- В UI есть кросс-проектная страница открытых MR/PR с клиентскими фильтрами по scope, поиску,
  автору, target и draft; она использует существующий `reviews.remoteList` по каждому
  зарегистрированному проекту и открывает read-only preview или полное ревью. При открытии из
  списка запоминается origin, поэтому preview/ревью показывают кликабельные крошки; возврат
  восстанавливает фильтры и скролл.
- Тема, язык интерфейса, справка и видимость раздела «Фичи» находятся на отдельной странице
  настроек; тема и видимость сохраняются локально.
- Просмотр MR/PR без ревью: `POST /api/previews/open` получает info, diff и треды в короткоживущий кэш;
  preview-маршрут скрывает замечания, комментарии, реакции и публикацию и не создаёт запись ревью
  или событие метрик.
- Метрики качества по проекту считаются из append-only журнала `review_events`: acceptance,
  publish и rule-grounded, полнота coverage, время до первого замечания, цикл ревью, дубли/кандидаты в правила и акторы.
  Замечание может нести ссылку `rule`; события включают opened/synced, summary, findings, decisions,
  publish и checks.
- Контекст ревью несёт консервативный профиль риска (`low`/`medium`/`high`, режим `fast`/`full`) по
  путям и размеру diff. Выжимка хранит `coverage` и `unknowns`, поэтому пустой список замечаний не
  принимается за полностью проверенное ревью.
- Ревью сохраняет контекст мержа: target, базу/head diff и mergeability платформы
  (`clean`/`conflict`/`behind`/`unknown`/`unavailable`). Контекст и UI показывают конфликт или
  отставание от target до того, как агент сделает выводы.
- Треды и замечания виртуализируются после 30 карточек: измеренные страницы по 10 рендерятся только
  при попадании во viewport, карточка с фокусом остаётся в DOM, deep-link прокручивает к нужной странице.
- Unified diff с hunks по файлам, номерами строк в старой/новой версии, фильтром файлов и отметкой
  «просмотрено» для каждого ревью. Файлы сгруппированы в сворачиваемое дерево папок, которое можно
  скрыть и менять в ширине, а скрытые неизменённые строки вокруг hunks раскрываются на месте
  (по 10 строк или все сразу); полный файл отдаётся из локального коммита или raw API платформы.
  Открытые треды и замечания рендерятся прямо под строками; в треде можно быстро ответить, но
  публикация всё равно требует подтверждения, а «Открыть» переходит на полную вкладку.
- Треды: чтение, ответ, резолв, реакции; комментарии человека к строкам; реакции на MR/PR и заметки.
- Поиск по diff: поиск в открытом файле со счётчиком и переходами вперёд/назад, плюс сохраняемый
  режим переноса длинных строк.
- Suggested changes: композер комментария к строке подставляет блок ```suggestion с текущей строкой,
  а платформа показывает нативную кнопку применения после подтверждения публикации.
- CODEOWNERS: обзор находит владельцев изменённых файлов в рабочей копии или head платформы и
  связывает каждый файл с Diff.
- Необязательные браузерные уведомления о новых открытых тредах, пока вкладка в фоне; разрешение
  запрашивается в настройках, выбор хранится в `localStorage`.
- Инкрементальный ре-ревью: UI хранит отмеченный как просмотренный head и показывает баннер при
  смене head, с числом устаревших замечаний, ссылкой на diff и действием «отметить просмотренным».
- Готовность к мержу в обзоре: GitHub check runs или последний pipeline GitLab, approvals, конфликты,
  отставание от target и открытые треды, со ссылками на проверки и ручным обновлением. Endpoint
  только читает и кешируется на 60 секунд.
- Публикация выжимки ревью: сохранённая выжимка (изменения, фокус, coverage, unknowns) уходит как
  review в GitHub с вердиктом `approve`/`request_changes`/`comment` или как заметка в GitLab плюс
  approve/unapprove. Хеш плана покрывает точный текст и вердикт; публикует только человек.
  При наведении или фокусе на реакцию видны количество и имена поставивших.
- Редактирование и удаление своих комментариев платформы.
- Вложения: загрузка растровых картинок и видео в GitLab project uploads с markdown-ссылкой; GitHub
  не поддерживает публичный API загрузки.
- Выжимка ревью, замечания с уровнем (`blocker`/`major`/`minor`/`question`), стабильные id,
  решения (`accept`/`reject`/`discuss`), приватные заметки агента и статус публикации.
- Многоагентные роли и шарды (`review.agents`, `review.roles`, кастомные роли); демон хранит
  итоговый результат лида.
- Аналитика: принятые/отклонённые/ожидающие замечания, acceptance rate, треды, черновики,
  отклонённые предложения.
- Опциональный скан секретов с маскированными превью.
- Опциональная история версий ревью по head/base SHA.
- Группы изменений: явные или автоматические по типу файла/модулю.
- Проверки проекта: argv, привязка к путям; агент только планирует, человек запускает в UI или CLI на хосте с показом полной команды.
- Read-only ревью: черновики, замечания, комментарии, реакции, проверки и публикация отключены.
- Экспорт/импорт старого файлового формата.

## Интерфейсы агента

- **MCP-сервер** поверх stdio: status, list, open, context, threads, diff, rules, draft replies,
  draft findings, summary, line notes, сообщения агенту, feature context/notes, publish preview и publish.
- **CLI** с теми же возможностями для харнессов без MCP.
- **Явные точки входа сценариев**: `revdeck review` / `revdeck feedback` и `/revdeck review|feedback`
  фиксируют «чужой MR» или «свой MR» до старта агента. `revdeck_context` принимает
  `scenario=review|feedback`; `revdeck open` остаётся нейтральным и подсказывает подходящую команду.
  В контексте есть `scenario`, `suggestedScenario` и отметка, ваш ли это MR.
- **Skill** (`skills/revdeck`) с процедурой ревью, критериями, разбором фидбека и кросс-проектным
  workflow.
- MCP-промпты `review-mr`, `close-feedback` и `review-feature`; они соответствуют командам `review`,
  `feedback` и работе с фичей.
- Детерминированный контекст с ограничением размера: выжимка, изменённые файлы, эффективные правила,
  треды, замечания, черновики и следующие действия.
- Агент не публикует, не резолвит треды, не делает approve/merge и не вызывает платформенные CLI
  напрямую.
- Публикация требует approval, привязанного к хешу точного плана; `publish.commit` идемпотентен и
  пропускает уже отправленное.

## Проекты

Проект — это репозиторий, а не «фронтенд» или «бэкенд».

- Стабильный ключ `platform:host/project`, нормализованный для сравнения; отображаемые значения
  хранятся отдельно.
- Реестр проектов и root'ов рабочих копий (`projects`, `project_roots`); у одного проекта может быть
  несколько клонов/worktree.
- Ревью хранят `projectKey`; UI, HTTP API и CLI умеют фильтровать по проекту или root'у.
- `revdeck projects` показывает проекты, root'ы и число ревью; `revdeck projects add <path>`
  регистрирует проект до первого ревью.
- В UI — переключатель проектов и домашний экран; видны только ревью выбранного проекта. Выбор
  хранится в URL и localStorage. На домашнем экране можно добавить проект, изменить отображаемое
  название и root'ы рабочих копий, удалить проект вместе с локальными ревью. Удаление не трогает
  MR/PR и комментарии на платформе.
- MCP-сервер ограничен репозиторием, в котором запущен: status/list/open видят только этот проект, а
  id или URL чужого ревью отклоняется. `REVDECK_ROOT` поддерживает multi-root workspace.
- Devcontainer'ы монтируют стабильный мост к демону хоста; контейнер не запускает свой демон.
- Кросс-проектная работа возможна только через явную фичу.

## Фичи

Фича — созданный человеком набор ревью из одного или нескольких проектов. Это не проект и не
постоянная связь проектов; проект присутствует в фиче, пока в ней есть хотя бы одно его ревью.

- Название, Markdown-бриф (цель, non-goals, порядок выката, критерии), отдельный контракт Markdown или
  OpenAPI, статус (`open`/`archived`).
- Упорядоченные ревью со свободными ролями (`api`, `ui`, `worker`, `mobile`); несколько ревью одного
  проекта разрешены.
- **Контракт OpenAPI:** разбирается на операции, параметры, тела запросов, ответы и схемы. Контекст
  фичи отмечает, какие изменённые ревью упоминают каждый путь.
- **Профили приложений:** `context.sources` / `context.maxBytes` в каждом репозитории; подключаются
  один раз на проект как фон, а не как критерии ревью.
- **Заметки/находки фичи:** кросс-проектные заметки на фиче, видны в UI и контексте. Никогда не
  публикуются. Человек пишет в UI/CLI; агент — только в feature-сессии через `revdeck_feature_note`,
  и может менять/удалять только заметки, созданные агентом. Текст заметок и профилей — данные, а не
  инструкции.
- **Project session:** видит свой проект и фичи, куда он входит; может читать общий контекст фичи, но
  черновики пишет только в свой проект.
- **Feature session:** запускается явно с `REVDECK_FEATURE=<id>`. Текущий репозиторий должен быть
  участником; скоуп ограничен участниками. Черновики можно писать в любого участника. Публикация
  остаётся по каждому ревью и требует подтверждения человека. Заметки фичи можно писать.
- Членство в фиче перепроверяется на вызовах инструментов: удаление текущего проекта/ревью отзывает
  доступ.
- Общий контекст: бриф, разобранный контракт или сырой Markdown, профили приложений, заметки фичи,
  матрица обзора и секция на каждое ревью с его правилами. Правила не смешиваются; бюджет делится
  между ревью.
- UI: список фич, страница фичи с группами проектов, ролями, контрактом, заметками, превью контекста,
  командой агенту, архивом, удалением, изменением порядка и добавлением ревью.
- CLI: `revdeck feature list|create|get|add|remove|reorder|notes|note|note-delete|context|update|archive|delete`.
- MCP: `revdeck_feature` (read-only list/get/context/notes) и `revdeck_feature_note` (только
  feature-сессия, никогда не публикуется).
- Удаление отслеживаемого ревью, входящего в фичу, блокируется, пока его не уберут из фичи.
- Публикации на уровне фичи нет; замечания и выжимки принадлежат ревью.

## Интерфейс

- Локальный Svelte 5 SPA, отдаваемый демоном, с launch-токеном (меняется при перезапуске) и cookie-сессией.
- Переключатель проектов, домашний экран проектов (добавление/изменение/удаление), список фич и
  страница фичи.
- Вкладки ревью: Обзор, Треды, Замечания, Diff, Правила, Аналитика.
- Горячие клавиши: `1`–`6` — вкладки; `o`, `r`, `s`, `p`, `?`/`⌘K`, `h` — глобально; в Diff `[`/`]`
  переключают файлы, `f` ставит фокус в фильтр, `t` скрывает/показывает дерево, `e`
  раскрывает/сворачивает скрытые строки, `v` отмечает файл просмотренным. `n`/`N` переключают inline-обсуждения. Буквенные сокращения идут
  по физической клавише (не зависят от раскладки) и пропускаются в полях ввода и диалогах. Палитра
  команд, deep links на треды, замечания и строки diff с рабочей кнопкой Back/Forward.
- Страница справки по командам (`#/help`): поиск по CLI, общие флаги и горячие клавиши, копирование
  команды кликом. Доступна из сайдбара и по `h`.
- Markdown-превью, кнопка вложения, реакции, комментарии к строкам, диалог публикации с точным планом.
- Русский и английский интерфейс; язык интерфейса не зависит от языка результатов ревью.
- В настройках выбираются тема, язык интерфейса, видимость «Фич» и интервал автообновления
  (выкл/10/30/60 мин, по умолчанию 10 мин). Автообновление выполняет тот же принудительный refresh, что и кнопка в шапке,
  пока открыто ревью или preview; тики пропускаются в фоновой вкладке, во время ввода и при открытых
  диалогах, а отсчёт начинается заново после любого ручного обновления.
- Новые релизы видны в UI: демон проверяет npm `latest` не чаще раза в сутки, `GET /api/update`
  отдаёт текущую/последнюю версию и ссылку на релиз, в сайдбаре видны версия и бейдж обновления, на
  страницах ревью — закрываемый баннер, а в настройках карточка «О программе» с ручной проверкой и
  командой обновления npm. `REVDECK_UPDATE_CHECK=0` отключает проверку; телеметрии и автоустановки
  нет.
- Адаптивный сайдбар и мобильный backdrop; светлая/тёмная тема через CSS-переменные.

## Безопасность и доверие

- Unix-сокет с каталогом `0700` и сокетом `0600`; UI только loopback; проверки `Host`/`Origin`,
  cookie `HttpOnly` `SameSite=Strict`, CSP.
- Уведомление об обновлении работает через pull: демон обращается к `registry.npmjs.org` не чаще
  раза в сутки, не передаёт идентификаторов кроме User-Agent `revdeck/<version>`, ничего не
  скачивает и не устанавливает; отключается через `REVDECK_UPDATE_CHECK=0`.
- Мост devcontainer — агентский (`read`/`draft`): `publish.*`, `checks.run`, решения, записи в
  платформу и администрирование фич/проектов возвращают `CAPABILITY`. Токен UI в контейнер не
  монтируется.
- Документы правил/профилей должны быть отслеживаемы git, иметь безопасное расширение и не быть
  локальным секретом (`.env*`, `.git/config`, `.npmrc`, `.revdeck.local.*`, ключи); чтение проверяет
  realpath уже открытого fd, закрывая symlink-TOCTOU.
- Вызовы платформенных CLI без shell, вне рабочей копии, с вычищенным окружением; секреты
  редактируются в логах и ошибках.
- Текст MR, комментарии и diff — недоверенные данные; skill и контекст это оговаривают.
- Санитайзер комментариев блокирует HTML, управляющие/bidi-символы, быстрые команды GitLab и массовые
  упоминания; внешние картинки — ссылки, а не загрузки.
- Approval случайный, одноразовый, с TTL и привязкой к ревью и хешу плана.
- Скоупы проектов и фич — **изоляция контекста**, а не security boundary: остаются один демон и одна
  база. Мост ограничивает записи, но read-методы всё ещё видят локальную базу; процесс с доступом к
  домашнему каталогу может её прочитать.
- Жёсткая изоляция требует отдельного демона/state-каталога под другим пользователем/контейнером; это
  вне текущей модели и ломает кросс-проектное ревью.

## Конфигурация

`.revdeck.yml` (или `.revdeck.yaml`) в корне репозитория с личными overrides в `.revdeck.local.yml`:

- `version`, `provider` (`type`, `host`, `project`, `base`), `output.language`.
- `review`: agents, roles, custom roles, groups, secrets, history, readOnly.
- `context`: источники профилей приложений и `maxBytes`.
- `rules`: sources, карта путей, ignore, лимиты документов/общего размера.
- `checks`: id, name, argv, условия по путям, consent, timeout.
- `publish`: требование approval, максимум комментариев.

Явные аргументы CLI важнее конфига, конфиг важнее git remote; так подмена `.git/config` не перенаправит
ревью. Схема проверяется zod, неизвестное поле — ошибка с путём.

## Эксплуатация

- `revdeck init`: конфиг, skill, адаптеры харнессов и MCP-конфиг; идемпотентно, не перезаписывает
  чужие ключи.
- `revdeck eject`: обратная операция; по умолчанию план, `--yes` для применения, `--keep-config`
  оставляет конфиг.
- `revdeck doctor`: Node, git, авторизация `glab`/`gh`, демон, адаптеры; знает про devcontainer.
- Жизненный цикл демона: start/stop/restart/status/logs/install/uninstall; systemd user unit на Linux,
  launchd на macOS.
- Мост devcontainer: стабильные mounts сокета/state; `glab`/`gh` на хосте; демон в контейнере не
  запускается.
- HTTP-транспорт для контейнеров без проброса сокета (`REVDECK_URL`, `REVDECK_TOKEN`).
- Экспорт/импорт для песочниц без сокета.
- Автозапуск на Linux и macOS; Windows — вручную.

## Архитектурные решения

### Демон-first

Долгоживущий пользовательский демон держит credentials, SQLite, провайдеры, RPC, HTTP/SSE и UI. CLI и
MCP — тонкие клиенты. Альтернатива — MCP-процесс на сессию без демона — отклонена: UI не переживает
сессию, агенты конкурируют за состояние, токен оказывается в процессе агента, а контейнерам всё равно
нужен процесс на хосте. Файловый обмен остался только как `export`/`import`.

Последствия: жизненный цикл демона, права сокета, мост для контейнеров, совпадение версий клиентов,
фоновый sync и SSE. Один демон обслуживает несколько репозиториев; `root` передаётся при открытии, а
конфиг читается из этого root'а. Клиент в devcontainer передаёт путь рабочей копии на хосте
(`REVDECK_HOST_ROOT`), а не путь монтирования в контейнере, поэтому демон хоста видит конфиг и правила.

### Скоупы проектов

Проект — это репозиторий. Ключ `platform:host/project`; ревью хранят его, а демон ведёт реестр с
root'ами рабочих копий. UI и CLI работают в скоупе проекта; MCP-сервер ограничен репозиторием, в
котором запущен. Отдельный демон/база на проект отклонены: это ломает кросс-проектное ревью, добавляет
порты/сервисы/бэкапы и всё равно не защищает от того же пользователя.

Последствия: миграция/backfill, ошибки MCP про чужой проект, настройка multi-root workspace и
изоляция только на уровне контекста.

### Явные фичи

Поскольку проекты изолированы, кросс-проектная работа требует явной созданной человеком фичи. Фича —
единственная дверь: состав выбирается на задачу; project-сессии читают общий контекст, но пишут только
в свой проект; feature-сессия может писать по участникам, публикация — по каждому ревью. Постоянная
связь проектов или автоматическое кросс-проектное обнаружение отклонены: они протекают в несвязанные
задачи.

Последствия: заметки фичи не публикуются, контракт и профили предоставляет человек, feature-сессия
запускается явно, а удаление членства отзывает доступ на следующем вызове инструмента.

## Не цели и ограничения

- Замена нативного diff-вьюера GitLab/GitHub; UI — для триажа и подтверждения.
- Собственный статический анализ; проверки делегируются инструментам проекта.
- Многопользовательский сервер и ролевая авторизация.
- Жёсткая security-изоляция проектов; см. оговорку выше.
- Native draft notes/pending review (провайдеры готовы, публикация идёт обычными комментариями).
- Загрузка вложений в GitHub через публичный API.
- Автоматическая статическая валидация клиентов по OpenAPI: контракт разбирается и передаётся агенту,
  реализацию проверяет агент.
- Публикация на уровне фичи или автоматическая публикация всей фичи.
- Checkout исходников чужих репозиториев в контексте фичи: только данные ревью, профили и контракты.
