# Архитектура

[English](../architecture.md) | Русский

## Цели

1. Агент получает контекст ревью и правила проекта детерминированно, без ручных файлов и без доступа
   к токенам платформ.
2. Публикация в GitLab/GitHub происходит только после подтверждения человеком и идемпотентна.
3. Один инструмент работает в любом харнессе: MCP для агентских клиентов, CLI как универсальный
   слой, веб-интерфейс для человека.
4. Правила проекта конфигурируются, а не зашиты в промпт.

## Не цели

- Замена нативного diff-вьюера GitLab/GitHub. UI оптимизирован под триаж и подтверждение.
- Собственный статический анализ. Проверки делегируются линту, типам и тестам проекта.
- Многопользовательский сервер. Модель — один пользователь, несколько репозиториев и ревью, демон на хосте.

## Компоненты

```text
agent (MCP/CLI) ──▶ revdeck daemon ──glab/gh──▶ GitLab/GitHub
                         │
                   SQLite + UI ◀── human
```

- `src/core` — чистые функции и модели: идентичность и ключи проектов, парсер unified diff, правила, fingerprints замечаний,
  санитайзер публикации, редакция секретов, безопасный запуск процессов.
- `src/providers` — единственное место, знающее о платформах. `Provider` нормализует MR/PR, diff,
  полное содержимое файла на коммите, треды, ответы, резолв и создание комментариев.
- `src/daemon/service.ts` — оркестратор: обновление ревью, черновики, решения, план публикации,
  approval, идемпотентная запись, фоновый sync.
- `src/daemon/store.ts` — SQLite (`node:sqlite`): проекты и их root'ы, ревью, снимок diff/тредов,
  черновики, замечания, решения, комментарии, approvals, аудит.
- `src/daemon/rpc.ts` — JSON-RPC поверх unix-сокета (0600) для CLI и MCP.
- `src/daemon/bridge.ts` — дополнительный agent-scoped RPC-сокет в стабильном домашнем каталоге для devcontainer (без publish/checks/admin и без токена UI).
- `src/daemon/http.ts` — UI и `/api/*`, SSE-события, cookie-сессия с launch-токеном (в контейнер не монтируется).
- `src/cli` — команды, `init`, `doctor`, экспорт/импорт старого файлового формата.
- `src/mcp` — MCP-сервер: инструменты и промпты, тонкая обёртка над RPC.
- `ui` — Svelte 5 SPA, собирается в `dist/ui`.

## Поток данных

1. `revdeck open 42` → RPC `reviews.open` с `root` рабочей копии; проект определяется по конфигу/remote и регистрируется.
2. Демон определяет платформу/хост/проект (аргументы → конфиг → git remote), создаёт провайдер,
   читает MR, diff и треды, сохраняет снимок и синтетические черновики.
3. Агент запрашивает `revdeck_context`: демон собирает эффективные правила (документы и секции для
   изменённых путей), сниппеты, треды и замечания.
4. Агент пишет черновики (`drafts.put`, `findings.put`, `summary.put`, `notes.update`).
5. Человек в UI или CLI на хосте вызывает `publish.preview` → видит точный план и хеш →
   `publish.approve` → `publish.commit`. У моста нет approve/commit (`CAPABILITY`); демон выполняет
   только пункты, вошедшие в подтверждённый план.
6. Фоновый sync раз в 2 минуты обновляет открытые ревью и рассылает SSE-события UI.
7. UI читает ревью из кешированного снимка (`/api/state`); устаревший снимок обновляется в фоне, а
   результат приходит по SSE, поэтому открытие не ждёт платформу.

`revdeck review 42` и `revdeck feedback 42` — тонкие CLI-обёртки над тем же путём `reviews.open` +
`rules.get`. Сценарий — клиентская опция контекста: она задаёт инструкции агенту, но не сохраняется в
ревью, демоне или базе.

## Модель данных

- `Project` — репозиторий: `key = platform:host/project` (нормализован для сравнения), отображаемые
  значения и один или несколько root'ов рабочей копии. У ревью тот же `projectKey`.
- `Feature` — явный набор ревью с брифом, контрактом и заметками; `FeatureReview` добавляет роль и
  порядок; `FeatureNote` хранит непубликуемые кросс-проектные заметки/находки.
- `ReviewRef` — платформа, хост, проект, номер. `reviewId` — `platform:host/project!number`.
- `DiffFile`/`Hunk`/`DiffLine` — номера строк по старой и новой версии; `line` замечания всегда по
  новому файлу.
- `previews` — in-memory снимки с TTL для просмотра MR/PR; используют `info`/`diff`/`threads`
  провайдера и не попадают в SQLite или список ревью.
- `review_events` — append-only журнал качества (актор, тип, finding/thread/rule, payload); метрики
  читают его, а не только текущий снимок.
- `ReviewInfo.merge` — mergeability на момент sync: target, база/head diff, детали платформы и
  `clean`/`conflict`/`behind`/`unknown`/`unavailable`. Это отдельно от merge-base diff.
- `Thread`/`Note` — общая модель обсуждений.
- `Finding` — замечание с `id`, `fingerprint`, уровнем, файлом/строкой, текстом и статусом
  (`draft`, `accepted`, `rejected`, `published`, `fixed`, `stale`).
- `Approval` — одноразовый id, привязанный к `hash = sha256(canonicalJson({reviewId, kind, items}))`,
  TTL 10 минут.

## Проекты и изоляция

Один демон обслуживает несколько репозиториев. **Проект** — это один репозиторий с ключом
`platform:host/project`; ревью хранит ключ проекта и свой root рабочей копии. Реестр демона
(`projects`, `project_roots`) заполняется при открытии ревью или при явной регистрации
(`revdeck projects add <path>`).

- UI выбирает один проект за раз: переключатель, домашний экран и очередь ревью в скоупе выбора.
  Выбор хранится в URL и localStorage. На домашнем экране можно зарегистрировать рабочую копию,
  изменить название и root'ы, удалить проект вместе с локальными ревью; удаление не обращается к
  платформе.
- MCP-сервер — точка изоляции. Он определяет проект по `REVDECK_ROOT` (или текущему каталогу),
  показывает только этот проект и отклоняет id/URL чужих ревью. Агенту не доступны `root` и
  override проекта.
- `reviews.list` принимает `project` или `root`; это фильтр для UI/CLI, а не security boundary.
  Остаются один демон и одна база; процесс с доступом к домашнему каталогу может прочитать базу.
- Кросс-проектная работа не подразумевается. Созданная человеком фича связывает ревью из
  нескольких проектов; вне неё чужое ревью отклоняется. См. [возможности](capabilities.md#скоупы-проектов)
  и [Фичи](capabilities.md#фичи).

## Фичи

**Фича** — созданный человеком набор ревью из разных проектов. Это не проект и не постоянная связь
проектов: проект присутствует, пока в фиче есть хотя бы одно его ревью. `features` хранит название,
Markdown-бриф, отдельный контракт Markdown/OpenAPI, статус и заметки человека/агента;
`feature_reviews` — состав, свободную роль и порядок. Несколько ревью одного проекта разрешены.
OpenAPI разбирается на операции и схемы, а контекст отмечает, какие изменённые ревью упоминают
операцию. Профили приложений — фоновые документы в `context.sources` каждого репозитория
(`context.maxBytes` ограничивает размер).

- UI и CLI создают/редактируют фичи; MCP даёт read-only обнаружение/контекст, а в feature-сессии —
  `revdeck_feature_note` для заметок, созданных агентом (никогда не публикуются).
- **Project session** видит фичи, куда входит его проект, может читать общий контекст, но пишет
  только в свой проект.
- **Feature session** запускается явно (`REVDECK_FEATURE=<id>`): текущий репозиторий должен быть
  участником, скоуп ограничен участниками, черновики можно писать в любого. Публикация остаётся по
  каждому ревью и требует подтверждения.
- Общий контекст: бриф, контракт (разобранный OpenAPI или Markdown), профили приложений, заметки
  фичи, матрица обзора и секция на каждое ревью с его правилами. Правила не смешиваются. Бюджет
  делится между ревью.
- Публикации на уровне фичи нет. Замечания и выжимки принадлежат ревью; заметки/находки фичи — не
  публикуемый блокнот для кросс-проектных наблюдений. Фича агрегирует ревью для навигации. См.
  [возможности](capabilities.md#фичи).

## Идемпотентность и конкурентность

- Записи черновиков и замечаний идут через один процесс; SQLite в WAL.
- Публикация помечает approval использованным до выполнения. Пункты, которые уже ушли (совпадающий
  `posted`, `published`), пропускаются. Ошибка одного пункта не отменяет остальные и записывается в
  черновик/замечание.
- Хеш плана защищает от правки агентом между показом человеку и публикацией: изменился текст → хеш
  не совпал → approve отклонён.
- `findings.put` — замена набора с сохранением `id` и решения; исчезнувшие замечания помечаются
  `stale`, а не удаляются.

## Расширение

- **Новая платформа**: реализовать `Provider` и добавить ветку в `createProvider`; всё остальное не
  меняется.
- **Новый харнесс**: `revdeck init --adapters <имя>` пишет MCP-конфиг или файл команды и ссылается на
  канонический skill `.agents/skills/revdeck`. Для
  харнессов без MCP используется CLI.
- **Правила**: `rules.map`/`rules.sources` в `.revdeck.yml`; паки правил можно распространять как
  обычный файл конфигурации.
- **Проверки**: `checks` с argv; агент только планирует, человек запускает в UI или CLI на хосте;
  мост запрещает `checks.run`.

## Производительность

- Diff парсится на сервере, UI получает файлы списком и hunks по одному файлу. Раскрытие скрытых
  строк запрашивает `/api/file`: сервис сначала пробует `git show <sha>:<path>` в root ревью,
  затем raw API провайдера, и кэширует разобранные строки на 10 минут.
- Состояние ревью не содержит полный diff; SSE сообщает об изменениях, UI перезапрашивает состояние.
- Открытие ревью отдаёт кешированный снимок; устаревший обновляется в фоне. Однослотовый кеш
  разобранного снимка и один индекс сниппетов на view удешевляют большие ревью.
- Heartbeat'ы SSE отключают поллинг-страховку; события review/feature/project обновляют только свою
  часть, а неизменившиеся списки в UI не переприсваиваются.
- Треды и замечания используют измеряемый page-windowed virtual list в UI: в DOM только видимые
  страницы, а фокус, редакторы и deep-link'и остаются рабочими.
- Сниппеты для тредов и замечаний считаются на сервере и ограничены по размеру.
- Размер контекста правил задают `rules.maxDocumentBytes` и `rules.maxTotalBytes` (`0` — без
  ограничения); MCP-контекст дополнительно ограничивается параметром `max_bytes`.
